## 1. Elevator Pitch

A simple, modular personal finance manager built in Python that tracks income and
expenses, maintains a single shared balance across the whole application, converts
third-party freelance income into a native format, and proactively notifies the user
when their balance drops below a threshold - all while keeping components decoupled
through classic object-oriented design patterns and constructor-based dependency
injection.

---

## 2. Architecture & Design Decisions

The application is organized as a set of small packages, each owning one responsibility:

- **`balance/`** - the `Balance` singleton (shared state) plus the observer infrastructure.
- **`transaction/`** - the `Transaction` domain model, the `TransactionCategory` enum,
  and the `TransactionAdapter` that bridges external data into the domain model.
- **`strategy/`** - pluggable budget-planning strategies (the fourth pattern).
- **`main.py`** - the composition root. It constructs components and wires them
  together using constructor injection.

### Key design decisions

1. **Singleton via `__new__`.** `Balance` guarantees exactly one instance app-wide,
   which is what we want for a single "net worth" number. `_instance` is guarded by
   `__new__`, and instance attributes are initialized on first creation so they are
   not reset by later constructor calls.

2. **Observer callbacks receive the transaction.** `notify_observers(transaction)`
   passes both the new balance and the transaction that caused it, giving observers
   (e.g., a low-balance alert, a console printer) everything they need to react.

3. **Constructor injection in the composition root.** Rather than hard-coding which
   observers exist, `main.py` creates the observers and passes them in via
   `register_observer`. This keeps `Balance` ignorant of concrete observer classes and
   makes it trivial to swap in mocks in tests.

4. **Strategy selection at runtime.** Budget allocation is a behavior that varies
   (50/30/20 vs. zero-based), so it is encapsulated behind an `IBudgetStrategy`
   interface. `main.py` picks the strategy and passes the balance to it - the caller
   does not need to know the internals.

## 3. Design Patterns in Practice

### Singleton - `Balance`

- **Where:** `balance/balance.py`.
- **Why:** The application needs exactly one shared balance; every transaction must
  mutate the same number. `Balance.get_instance()` always returns the same object
  (verified by `test_singleton_instance`).
- **Trade-off:** Singletons are global state, which can complicate testing. I
  mitigated this by keeping the class small and exposing `reset()`, which resets
  both the balance and the observer list, so tests start from a clean baseline.

### Adapter - `TransactionAdapter`

- **Where:** `transaction/transaction_adapter.py`.
- **Why:** A third-party freelance platform exposes `ExternalFreelanceIncome`
  (amount, invoice id, description, a fixed `typ = "income"`). The adapter maps that
  foreign shape onto the internal `Transaction` contract so the rest of the app never
  sees the external format. Crucially, it preserves the external metadata - the
  `invoice_id` and `description` - so the adapted record retains its source context
  for finance tracking.
- **Trade-off:** The adapter is currently single-source; supporting many external
  vendors would warrant a family of adapters behind a common interface.

### Observer - `PrintObserver` / `LowBalanceAlertObserver`

- **Where:** `balance/balance_observer.py`; registration in `Balance`.
- **Why:** "React to balance changes" is a classic publish/subscribe problem. The
  `Balance` publishes; the alert observer fires only when the balance crosses below
  its threshold, and the print observer logs every change. Adding a new reaction
  (email, push notification) requires no change to `Balance`.
- **Trade-off:** Notifications are synchronous; a slow observer blocks the balance
  update. Acceptable for this scale.

### Strategy (student's choice) - `IBudgetStrategy` / `FiftyThirtyTwentyStrategy` / `ZeroBasedBudgetStrategy`

- **Where:** `strategy/budget_strategy.py`.
- **Why chosen:** Budget planning is an ideal Strategy use case - the *algorithm*
  varies (50/30/20 rule vs. zero-based budgeting) but the *interface* is stable. It
  lets users switch budgeting methods without touching the transaction pipeline.
- **How it improves flexibility/testability/scalability:** new budgeting rules can be
  added as new strategy classes; the same tests validate all strategies through the
  common interface (`test_strategy_interchangeability`); and the strategy can be
  swapped at runtime.

## 5. Testing Philosophy

- **Framework:** Python's built-in `unittest` (no third-party dependencies).
- **Scope:** one test module per concern:
  - `test_balance.py` - singleton identity, income/expense math, reset, invalid category.
  - `test_transaction.py` - construction, string form, equality, hashability, and metadata.
  - `test_transaction_adapter.py` - external income converts to an equal native Transaction,
    including invoice id and description.
  - `test_balance_observer.py` - the alert toggles on/off at the exact threshold; PrintObserver
    output verified via `unittest.mock.patch('builtins.print')`.
  - `test_budget_strategy.py` - allocation math and interchangeability.
- **Isolation:** each balance test calls `reset()` in `setUp`, which clears both the balance
  and the observer list, so state never leaks between tests.
- **Outcome:** 20 tests, all passing.

## 6. Challenges & Resolutions

| Challenge | Resolution |
| :--- | :--- |
| Singleton state leaking across tests | `reset()` clears both `_balance` and `_observers`; instance state initialized once in `__new__`. |
| Observer test expects `alert_triggered` to toggle both ways | Implemented `update()` as an assignment (`balance < threshold`), so the flag reflects the *current* state rather than a one-shot latch. |
| Import layout for `python -m unittest discover` | Added `__init__.py` to every package and run tests from the `starter/` directory. |
| Keeping `Balance` decoupled from alerting | Constructor/registration injection in `main.py` - the composition root. |
| Transaction unhashable after overriding `__eq__` | Added `__hash__` based on `(amount, category)` tuple for consistency and to enable use in sets/dicts. |
| Missing unit test for PrintObserver | Added `TestPrintObserver` using `unittest.mock.patch('builtins.print')` to capture and verify output. |
| Adapter dropped invoice id and project description | Extended `Transaction` with optional `invoice_id`/`description` fields, populated them in the adapter, and asserted their survival in the adapter test. |
| PEP 8 violations (E302, E305, E501, W391) | Added blank lines around top-level definitions, wrapped long lines under 79 chars, and removed trailing blank lines; verified with `pycodestyle`. |

## 7. Review & Refinement

- Reviewed the observer contract against `test_balance_observer.py` before writing
  logic, so the flag semantics matched the expected behavior on the first pass.
- Re-checked `__str__` formatting against the exact expected string in
  `test_transaction_str`.
- Confirmed the adapter output satisfies the equality assertion in
  `test_transaction_adapter.py` (`Transaction(500, INCOME)`).
- **Cleanup pass:** After the initial implementation, a code review identified and
  resolved five minor concerns:
  - Added `__hash__` to `Transaction` to restore hashability after overriding `__eq__`.
  - Updated `Balance.reset()` to also clear `_observers`, preventing observer
    accumulation across test methods on the Singleton.
  - Fixed misleading `__init__` docstring in `Balance` to accurately describe its
    no-op behavior.
  - Added `TestPrintObserver` using `unittest.mock.patch` to cover the previously
    untested `PrintObserver` class.
  - Removed trailing whitespace for PEP8 cleanliness.
- **Resubmission pass:** Review feedback identified two remaining requirements:
  - Extended `Transaction` with optional `invoice_id` and `description` fields and
    populated them in `TransactionAdapter.to_transaction()`, so adapted freelance
    income retains its invoice and project context.
  - Resolved all PEP 8 violations (E302, E305, E501, W391) across the modules by
    adding required blank lines, wrapping long lines, and removing trailing blank
    lines; confirmed clean via `pycodestyle`.

## 10. Retrospective

The design patterns each solved a real, observable problem: the Singleton kept the
balance consistent, the Adapter insulated the domain from a foreign format, the
Observer made alerting/printing extensible without touching `Balance`, and the
Strategy made budgeting a swappable behavior. The biggest win was dependency
injection in the composition root - it made the components independently testable
and the application easy to extend. The main trade-off is the inherent global-state
nature of the Singleton, which is acceptable here because a single shared balance is
precisely the domain requirement. The cleanup pass after initial implementation
demonstrated the value of code review: small issues like missing `__hash__` and
observer accumulation in tests were caught and resolved, resulting in a more robust
and maintainable codebase. A final resubmission pass tightened the remaining loose
ends - the adapter now preserves invoice and project metadata so adapted transactions
keep their source context, and the full module set passes PEP 8 style checks with
zero violations - leaving the project compliant with the grading criteria.
